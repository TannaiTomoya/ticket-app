# 設計判断

作りながら気づいた問題と、それに対して決めたことの記録。データの持ち方（残り枚数を保存しない、金額は円の整数など）は [データベース設計](database.md) の「設計判断」を参照。

状態の見方: **実装済み** はコードとテストがあるもの、**予定** はこれから実装するときに従うもの。

<br>

## 在庫と購入

### 1. 支払い待ちの注文も枠を押さえる前提で、定員の下限を決める（予定）

- **状況**: 支払い待ちの注文は、作成から35分間は枠を押さえている。定員を「支払い済みの枚数」まで下げられると、その直後に支払い待ちの注文が支払われ、定員を超えて売れてしまう
- **決めたこと**: 券種の定員を下げるときの下限は「支払い済み ＋ 確保中（35分以内の支払い待ち）」の枚数にする
- **理由**: 残り枚数の計算と同じ条件（`Order::holdingSeats()`）を使えば、表示と制約が食い違わない

### 2. 購入時は券種の行をロックしてから残り枚数を数える（予定）

- **状況**: 2人が同時に「残り1枚」を見て、両方とも買えてしまう
- **決めたこと**: 注文の作成はトランザクションの中で、選ばれた券種の行を `lockForUpdate` で読んでから、残り枚数と販売期間を確かめる。単価は画面から受け取らず、その時点の DB の価格を明細に保存する
- **理由**: 同じ券種の購入が順番に処理され、後から来た人は最新の残り枚数で判定される

### 3. 購入前に確認画面を挟む（予定）

- **状況**: 詳細画面から直接注文を作ると、金額を見ないまま枠だけが押さえられる
- **決めたこと**: 詳細で券種と枚数を選ぶ → 確認画面で合計を見る → 確定したときに初めて注文を作る。確認画面の内容は URL の値ではなく、毎回 DB から組み立て直す
- **理由**: 利用者が納得してから枠を押さえられる。URL を書き換えられても、金額は変わらない

<br>

## 決済

### 4. 枠を押さえる時間を、決済ページの期限より長くする

- **状況**: 外部の決済ページの有効期限は最短30分。枠を押さえる時間がそれより短いと、枠を手放したあとに支払いが完了し、定員を超えて売れる
- **決めたこと**: 決済ページの期限を30分（`CheckoutService::EXPIRES_MINUTES`）にし、枠を押さえる時間を35分（`Order::HOLD_MINUTES`）にする。期限切れになった決済ページの注文は pending のまま残す
- **理由**: 期限の30分より前に支払いは終わるので、支払われた注文の枠は必ずまだ押さえられている。5分の差は、Webhook の遅れと時計のずれのぶん

### 5. 中断したら、決済ページを失効させてから注文をキャンセルする

- **状況**: 決済ページから戻ってキャンセル扱いにしても、決済ページそのものは期限まで使える。ブラウザの「進む」で戻ると支払えてしまう
- **決めたこと**: 中断ページでは、先に決済ページを失効させ、成功したときだけ注文をキャンセルにする。失効できなかった（すでに支払い済みなど）ときは「確認中」として扱う
- **理由**: 「お金は払われたのに注文はキャンセル」という状態を作らない

### 6. 支払いの確定は1か所にまとめ、条件付きの更新で二重を防ぐ（予定）

- **状況**: 支払いの通知（Webhook）と完了画面での問い合わせは、どちらが先に来るか分からず、同時に来ることもある
- **決めたこと**: 確定は1つのメソッドだけで行う。`status` が支払い待ちの行だけを更新する条件付きの UPDATE にし、更新できたときだけチケットを発行してメールを送る。無料券だけの注文も同じメソッドで確定する
- **理由**: 「読んでから判断して書く」と、2つの経路が両方とも支払い待ちと判断してしまう。判断と書き込みを1回の UPDATE で同時に行えば、DB が一方だけを通す

<br>

## 認可と公開範囲

### 7. 権限の無い相手には、下書きの存在そのものを隠す（実装済み）

- **状況**: 403 を返すと「その URL に何かがある」ことが分かってしまう
- **決めたこと**: 下書き・非公開のイベントは、所有者と管理者以外には 404 を返す。ポリシーが `denyAsNotFound()` を返すので、画面側は `$this->authorize()` のまま
- **確かめ方**: `tests/Feature/Events/EventShowTest.php`

### 8. 値を変える操作では、毎回あらためて認可する（実装済み）

- **状況**: Livewire は画面を開いたときに `mount()` を1回だけ動かし、そのあとはボタンを押すたびにメソッドだけを呼ぶ。`mount()` だけで認可すると、一度開いた画面から保存や削除ができてしまう
- **決めたこと**: 保存・公開切り替え・削除・券種の追加などの各メソッドの先頭で `authorize()` する。子のデータ（券種など）は、必ず親のリレーション経由で探す（`$event->ticketTypes()->findOrFail($id)`）
- **確かめ方**: 画面を開いたあとに別の主催者へ切り替えて操作すると 403 になるテスト、他のイベントの券種 ID を渡すと 404 になるテスト（`tests/Feature/Organizer/`）

### 9. 売上画面は主催者と管理者の両方を通す（予定）

- **状況**: 主催者向けのルートは `role:organizer` で守っているので、同じグループに置くと管理者が入れない
- **決めたこと**: 売上画面のルートは `role:organizer,admin` とし、どのイベントを見られるかはポリシー（所有者か管理者）で決める

<br>

## イベントと券種の整合性

### 10. 券種が無いイベントは公開できない（実装済み）

- **状況**: 券種が0件のイベントを公開すると、一覧に出ても誰も買えない
- **決めたこと**: 公開には券種1件以上を必須にする。公開中のイベントでは最後の券種を削除できない（削除すると0件の公開イベントができてしまうため）
- **確かめ方**: `tests/Feature/Organizer/EventManagementTest.php`、`TicketTypeManagementTest.php`

### 11. 注文があるイベントは削除できない（実装済み）

- **状況**: 注文からイベントへの外部キーは restrict なので、支払い待ちの注文が1件でもあると、DB がイベントの削除を拒否する
- **決めたこと**: 削除の条件を「注文が1件でもあれば不可」とし、ポリシーで先に止める。画面では削除ボタンの代わりに理由を表示する。券種も、注文の明細があれば削除できない
- **理由**: DB の例外（500）を利用者に見せない

### 12. イベントの開始日時と、券種の販売終了の前後関係を両方向で守る（予定）

- **状況**: 券種の販売終了はイベントの開始日時以前にしているが、あとからイベントの開始日時を早めると、開催後も販売が続く状態になる
- **決めたこと**: イベントを保存するときにも、開始日時が券種の販売終了より前にならないかを確かめる

### 13. 管理者が非公開にしたイベントは、主催者が公開に戻せない（実装済み）

- **状況**: 問題があって管理者が非公開にしても、主催者がボタン1つで公開し直せてしまう
- **決めたこと**: 公開の切り替えはイベントの `update` 権限で守り、非公開（unpublished）のときは 403 にする。画面にはボタンを出さず、理由を表示する。タイトルの修正などは非公開のあいだも許す

<br>

## コードの置き場所

### 14. 入力の検証とロジックは、画面のファイルの外に置く（実装済み）

- **状況**: Livewire の単一ファイルコンポーネント（`⚡*.blade.php`）は型チェック（phpstan）の対象外。中に書いたロジックは型の誤りに気づけない
- **決めたこと**: 入力と検証はフォームオブジェクト（`app/Livewire/Forms/`）、注文や決済の処理はサービスクラス（`app/Services/`）に置く。外部の決済サービスを呼ぶのはサービスクラスの中だけにする
- **理由**: 型チェックとテストが効き、テストでは外部サービスのクラスだけを偽物に差し替えられる
